# Promail

Production-oriented full-stack email scheduling assignment using Express, TypeScript, Prisma/Postgres, BullMQ, Redis, Ethereal SMTP, Next.js, and Tailwind CSS.

## Local setup

Prerequisites: Node.js 20+, Docker Desktop, a Google OAuth web client, and a Google Identity Services client ID.

1. Copy `backend/.env.example` to `backend/.env` and set `GOOGLE_CLIENT_ID` and a strong `SESSION_SECRET`. Copy `frontend/.env.example` to `frontend/.env.local` and set the same Google client ID.
2. Start local infrastructure:

```powershell
docker compose up -d
```

Expected: `postgres` and `redis` are running on `localhost:5433` and `localhost:6380`. The compose file is local development only; both services use persistent named volumes and Redis AOF.

3. Install packages and apply the migration:

```powershell
cd backend
npm install
npx prisma migrate deploy
npm run seed:senders
```

Expected: Prisma reports `1 migration found` and the seed command reports `Seeded 3 Ethereal sender mailboxes`. Sender credentials are generated by `nodemailer.createTestAccount()` and stored in Postgres.

4. Start the API and worker in separate terminals:

```powershell
npm run dev
```

Expected: `API listening on http://localhost:4000`. Verify `http://localhost:4000/health` returns `{ "ok": true }`.

In another terminal, run `cd backend; npm run worker:dev`. Both processes use the same durable BullMQ queue.

For Render, deploy the API as a Web Service with `npm install && npm run build && npm start`, and deploy a separate Worker service from the same repository with `npm install && npm run build && npm run worker`. Configure the same hosted `DATABASE_URL`, `REDIS_URL`, `GOOGLE_CLIENT_ID`, and `SESSION_SECRET` on both services. Configure the Mailtrap Sandbox SMTP variables described below on both services. Do not use the local Docker URLs.

The API health endpoint verifies both dependencies: `https://your-backend.onrender.com/health` should return `{"ok":true,"postgres":"connected","redis":"connected"}`. The worker logs `Worker started`, `Redis connected`, and `Waiting for scheduled email jobs...` after connecting.

5. Start the frontend in a second terminal:

```powershell
cd frontend
npm install
npm run dev
```

Open `http://localhost:3000`, sign in with Google, upload a text/CSV lead export, and schedule a batch. The frontend extracts addresses with a tolerant email regex and shows the detected count.

## API smoke test

The schedule endpoint requires the httpOnly session cookie created by Google login. The easiest smoke test is the Compose modal. The equivalent request is:

```powershell
curl.exe -X POST http://localhost:4000/api/campaigns -H "Content-Type: application/json" -H "Cookie: scheduler_session=..." -d "{\"subject\":\"Hello\",\"body\":\"Test message\",\"recipients\":[\"recipient@example.com\"],\"startTime\":\"2026-08-21T14:00:00.000Z\",\"delayMs\":1000,\"hourlyLimit\":10}"
```

The response is a campaign with `scheduled_emails`. Visit Ethereal's preview URL from the Nodemailer result during a development send, or inspect the stored `messageId` and use the Ethereal preview lookup in a local debugger.

## SMTP Configuration

The assignment specifies **Ethereal Email** as the fake SMTP service. The application supports Ethereal through Nodemailer for local development and testing.

### Production Deployment

For the Render Free deployment, **Mailtrap Sandbox** is used instead of Ethereal because Render Free restricts outbound SMTP connections on the ports required by Ethereal.

Mailtrap is also a fake/testing SMTP service, so no real emails are delivered to actual recipients.

The deployed configuration uses:

```env
SMTP_HOST=sandbox.smtp.mailtrap.io
SMTP_PORT=2525
SMTP_USER=<MAILTRAP_USERNAME>
SMTP_PASSWORD=<MAILTRAP_PASSWORD>
SMTP_FROM=promail@test.com
```

## Architecture

`Campaign` stores the requested campaign settings plus `effectiveHourlyLimit = min(requestedHourlyLimit, MAX_EMAILS_PER_HOUR)`. Each recipient becomes a `ScheduledEmail` row whose own UUID is the BullMQ `jobId`. The initial time calculation fills each hour window with at most the effective campaign limit and at most the number of recipients that fit when spaced by `delayMs`; remaining recipients spill into later hour windows.

BullMQ delayed jobs are the only scheduler. On boot, recovery changes every `processing` row back to `scheduled`, queries all scheduled rows, and idempotently re-enqueues each UUID. Adding a job with an existing UUID is a safe no-op in Redis. Before SMTP, the worker performs a conditional Postgres update from `scheduled` to `processing`; a retry or second worker therefore sees a non-scheduled row and exits. A crash after claiming can be recovered on the next boot.

The worker uses a Redis Lua `EVAL` script containing GET, INCR, and EXPIRE as one atomic operation. The key is an hour-window key, optionally suffixed with sender ID when `RATE_LIMIT_SCOPE=per-sender`. Each job uses the minimum of its campaign effective limit and the global maximum. When the counter is full, the row returns to `scheduled`, the BullMQ job moves to the next hour with up to five seconds of jitter, and `DelayedError` prevents it being marked failed.

Pacing is also Redis-backed: a second atomic Redis script reserves the next send slot using `MIN(previous + MIN_SEND_DELAY_MS, now)`. This remains consistent across worker processes. Sender IDs are assigned round-robin when a campaign is created.

If 1000+ emails become due together, BullMQ makes them available but the worker concurrency, Redis pacing, and atomic hourly counter govern actual SMTP calls. Jobs beyond the hourly capacity are retained and delayed into later windows, with jitter reducing a top-of-hour herd. They are never dropped merely because a rate limit was reached.

## Verification

```powershell
cd backend
npm test
npm run typecheck
cd ..\frontend
npm run build
```

Current unit coverage includes atomic limiter invocation, scheduling-time window math, and the conditional idempotency claim. The tests mock Redis/Postgres and do not require live services.

To verify restart recovery manually, schedule a batch at least a few minutes ahead, stop the API with Ctrl+C, leave Docker running, start `npm run dev` again, and query the scheduled/sent tabs. Rows remain in Postgres, BullMQ jobs are keyed by UUID, and already-sent rows are skipped. For a processing recovery check, stop during a send, restart, and confirm the row is processed once after the stale `processing` reset. Inspect Ethereal previews and ensure each recipient has one `sentAt` and one message ID.

## Requirement checklist and trade-offs

- Postgres schema, migration, persistence, BullMQ delayed jobs, restart recovery, worker concurrency, pacing, atomic rate limiting, campaign limits, sender rotation, idempotency, Google token verification, httpOnly sessions, polling, upload parsing, skeleton/empty states, and focused tests are implemented.
- The worker is loaded by the API process for a compact local assignment deployment; running it as a separate process is a straightforward extraction of `src/worker.ts` and uses the same queue.
- Session values are signed opaque user IDs rather than a separate session table. For a larger product, rotate secrets and persist revocable sessions.
- Failed SMTP attempts are marked failed rather than automatically retried indefinitely; BullMQ retry policy can be added with an explicit business retry budget.
- The frontend uses a small inline UI layer rather than a component library, keeping the assignment dependency-light while preserving typed feature boundaries.
